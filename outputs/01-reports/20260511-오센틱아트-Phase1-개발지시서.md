## 개발 지시 — Priority 1: 운영 전 필수 (즉시 착수)

### P1-1. 주문 상태 업데이트 API 및 관리자 UI

**배경**  
현재 쇼핑몰 주문은 결제 후 `paid` 상태에서 멈춘다. 관리자가 배송을 처리할 API와 UI가 없어 쇼핑몰 운영이 불가능한 상태다.

**구현 범위**

1. **API: `PATCH /api/admin/orders/[id]/status`**
   - 인증: admin role 필수
   - Request Body:
     ```json
     {
       "status": "preparing" | "shipped" | "delivered" | "cancelled",
       "tracking_number": "string (shipped 시 필수)"
     }
     ```
   - 비즈니스 로직:
     - 상태 전이 순서 강제: `paid → preparing → shipped → delivered`
     - `cancelled`는 `paid`, `preparing` 상태에서만 허용
     - `shipped` 전환 시 `tracking_number` 없으면 400 반환
     - 상태 변경마다 `orders.updated_at` 갱신
   - `shipped` 전환 시: 구매자에게 발송 알림 이메일 발송
   - `cancelled` 전환 시: 토스페이먼츠 환불 API 호출 + 구매자 이메일

2. **관리자 UI: `/admin/orders` 페이지 개선**
   - 현재: 읽기 전용 목록
   - 변경: 각 주문 행에 다음 추가
     - 상태 드롭다운 (현재 상태 기준 다음 단계만 선택 가능)
     - 운송장 번호 입력 필드 (`shipped` 선택 시 활성화)
     - "저장" 버튼 (클릭 시 위 API 호출)
   - 저장 성공 시 페이지 리프레시 또는 해당 행 상태 즉시 반영

3. **이메일 템플릿 신규 2종**
   - `lib/email/templates/order-confirmed.ts`: 주문 접수 확인 (결제 완료 직후 발송)
   - `lib/email/templates/order-shipped.ts`: 발송 완료 + 운송장 번호 안내
   - 기존 `resend.ts`의 `sendEmail` 함수 재사용

**관련 파일**
- 신규: `app/api/admin/orders/[id]/status/route.ts`
- 수정: `app/(admin)/admin/orders/page.tsx`
- 신규: `lib/email/templates/order-confirmed.ts`
- 신규: `lib/email/templates/order-shipped.ts`
- 수정: `app/api/orders/create/route.ts` (결제 완료 후 order-confirmed 이메일 발송 추가)

### P1-3. 수업 완료 처리 자동화

**배경**  
`bookings.status`에 `completed` 값이 존재하지만, 이 상태로 전환되는 로직이 없다. 리뷰 작성 조건이 `completed` 상태를 전제로 하므로, 이 처리가 없으면 수강생이 리뷰를 작성할 수 없다.

**구현 범위**

1. **Cron 수정: `app/api/cron/expire-bookings/route.ts`**
   - 기존 만료 처리 로직에 완료 처리 추가:
     - 조건: `bookings.status = 'paid'` AND `class_schedules.end_at < now()`
     - 처리: `bookings.status → 'completed'`
   - 단일 Cron에서 처리하여 Vercel 실행 횟수 절약

2. **강사 수동 완료 처리 (선택)**
   - `/studio/schedules` 페이지의 지난 회차 목록에 "완료 처리" 버튼 추가
   - 버튼 클릭 시 해당 회차의 모든 `paid` 예약을 `completed`로 전환
   - API: `PATCH /api/studio/schedules/[id]/complete`

**참고**
- `class_schedules.end_at`이 null인 경우: `start_at + 3시간`을 기준으로 처리
- `completed` 전환 후 수강생에게 리뷰 요청 이메일 발송 (선택: 이메일 템플릿 신규 추가)

**관련 파일**
- 수정: `app/api/cron/expire-bookings/route.ts`
- 신규: `app/api/studio/schedules/[id]/complete/route.ts`
- 수정: `app/(instructor)/studio/schedules/ScheduleManager.tsx`

## 개발 지시 — Priority 2: 운영 품질 (Phase 1 초기)

### P2-1. 수강생 연락처 강사 공개

**배경**  
강사가 예약 확정 후 수강생에게 클래스 안내(장소, 준비물 등)를 전달하려면 연락처가 필요하다. 현재 예약 신청 목록에 이름만 보이고 전화번호가 노출되지 않는다.

**구현 범위**

1. **`/studio/requests` 예약 목록 개선**
   - 예약 승인 후(`approved`, `paid` 상태) 수강생 전화번호 표시
   - 표시 형태: `010-XXXX-XXXX` (마스킹 없이 전체 노출)
   - RLS: 강사 본인 클래스의 예약에 한해서만 접근 허용

2. **DB 쿼리 변경**
   - `bookings` 조회 시 `users!student_id(name, phone)` 조인 추가
   - `users` 테이블 RLS 정책 수정: 강사가 본인 클래스 수강생의 phone 조회 허용
     ```sql
     CREATE POLICY "instructor_read_student_phone" ON public.users
       FOR SELECT USING (
         EXISTS (
           SELECT 1 FROM public.bookings b
           JOIN public.class_schedules s ON s.id = b.schedule_id
           JOIN public.classes c ON c.id = s.class_id
           WHERE b.student_id = users.id
             AND c.instructor_id = auth.uid()
             AND b.status IN ('approved', 'paid', 'completed')
         )
       );
     ```

**관련 파일**
- 수정: `app/(instructor)/studio/requests/RequestsList.tsx`
- 수정: `supabase/migrations/` (신규 마이그레이션 파일 추가: `0005_instructor_student_phone_policy.sql`)

### P2-2. 강사 주도 회차 취소 및 자동 환불

**배경**  
강사 개인 사정(건강, 일정 충돌 등)으로 특정 회차를 취소해야 하는 경우가 발생할 수 있다. 현재 회차 삭제만 가능하고, 이미 예약된 수강생 환불 처리 로직이 없다.

**구현 범위**

1. **API: `POST /api/studio/schedules/[id]/cancel`**
   - 인증: 해당 클래스의 강사 본인만 허용
   - 처리 순서:
     1. 해당 회차의 `paid` 상태 예약 전부 조회
     2. 각 예약에 대해 토스페이먼츠 전액 환불 API 호출
     3. `bookings.status → 'refunded'`, `refund_amount = gross_amount`
     4. 수강생 전원에게 환불 안내 이메일 발송 (기존 `refund-complete.ts` 템플릿 재사용, 취소 사유 추가)
     5. `class_schedules` 삭제 (또는 `is_cancelled` 플래그 추가 방식으로 변경)
   - 취소 사유 입력 필수 (Request Body: `{ "reason": "string" }`)
   - 이미 수업 시작 후에는 취소 불가 (`start_at < now()` 시 400 반환)

2. **UI: `/studio/schedules` 회차 목록**
   - 각 회차 행에 "회차 취소" 버튼 추가
   - 클릭 시 확인 모달: "이 회차를 취소하면 예약된 수강생 N명에게 전액 환불됩니다. 계속하시겠습니까?"
   - 취소 사유 입력 텍스트 필드 포함

**관련 파일**
- 신규: `app/api/studio/schedules/[id]/cancel/route.ts`
- 수정: `app/(instructor)/studio/schedules/ScheduleManager.tsx`

### P2-5. 수강생 클래스 D-1 알림 이메일 Cron

**배경**  
수강생이 수업 하루 전에 장소·준비물 안내를 받지 못한다. 수업 당일 장소를 못 찾거나 준비물을 빠뜨리는 문제가 발생할 수 있다.

**구현 범위**

1. **Cron: `app/api/cron/class-reminder/route.ts`**
   - 실행 주기: 매일 오전 10시 (`0 1 * * *` UTC 기준 → KST 10시)
   - 처리:
     - 내일 수업 예정 `paid` 상태 예약 전부 조회
     - 조건: `class_schedules.start_at BETWEEN now() + interval '20 hours' AND now() + interval '28 hours'`
     - 수강생에게 안내 이메일 발송

2. **이메일 템플릿: `lib/email/templates/class-reminder.ts`**
   - 포함 정보: 수업명, 날짜/시간, 장소(location_address), 강사 연락처(전화번호)
   - 준비물은 클래스 `attributes.materials` 필드 사용 (없으면 섹션 생략)

3. **`vercel.json` cron 설정 추가**
   ```json
   { "path": "/api/cron/class-reminder", "schedule": "0 1 * * *" }
   ```

**관련 파일**
- 신규: `app/api/cron/class-reminder/route.ts`
- 신규: `lib/email/templates/class-reminder.ts`

## 개발 지시 — Priority 3: 지부장 역할 구현

### P3-1. DB 스키마 변경 및 마이그레이션

**배경**  
현재 `users.role`은 `student | instructor | admin` 3종류다. 지역별 강사 관리를 위한 지부장 역할이 없어, 관리자가 전국 모든 강사를 혼자 관리해야 한다.

**구현 범위**

1. **마이그레이션: `supabase/migrations/0006_branch_manager.sql`**

   ```sql
   -- 1. users.role에 branch_manager 추가
   ALTER TABLE public.users
     DROP CONSTRAINT users_role_check,
     ADD CONSTRAINT users_role_check
       CHECK (role IN ('student','instructor','admin','branch_manager'));

   -- 2. branches 테이블 신설
   CREATE TABLE public.branches (
     id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
     name text NOT NULL,
     region text NOT NULL UNIQUE,
     manager_id uuid REFERENCES public.users(id),
     commission_rate numeric(5,2) DEFAULT 0.00,
     created_at timestamptz DEFAULT now(),
     updated_at timestamptz DEFAULT now()
   );

   -- 3. instructor_profiles에 branch_id 추가
   ALTER TABLE public.instructor_profiles
     ADD COLUMN branch_id uuid REFERENCES public.branches(id);

   -- 4. RLS 활성화
   ALTER TABLE public.branches ENABLE ROW LEVEL SECURITY;

   -- 5. RLS 정책
   CREATE POLICY "branches_read" ON public.branches
     FOR SELECT USING (true);
   CREATE POLICY "branches_admin_write" ON public.branches
     FOR ALL USING (public.get_role() IN ('admin'));
   CREATE POLICY "branches_manager_read" ON public.branches
     FOR SELECT USING (manager_id = auth.uid() OR public.get_role() = 'admin');
   ```

### P4-1. 카카오 알림톡 연동 (선택 사항)

**배경**  
현재 모든 알림이 이메일로만 전달된다. 국내 서비스 특성상 카카오 알림톡이 이메일보다 열람률이 높다. 특히 수업 당일 알림, 예약 확정, 정산 알림 등은 즉각적인 확인이 필요하다.

**구현 범위**

1. **카카오 비즈니스 채널 개설 후 알림톡 채널 등록**
   - 카카오 비즈니스 API: 카카오 i 오픈 빌더 또는 솔라피(Solapi) 사용 권장

2. **알림톡 발송 우선순위**
   - 예약 신청 완료 (수강생)
   - 예약 승인 완료 (수강생)
   - 수업 D-1 리마인드 (수강생)
   - 새 예약 신청 알림 (강사)
   - 정산 완료 알림 (강사)
   - 배송 시작 알림 (구매자)

3. **구현 방식**
   - `lib/notifications/kakao.ts` 신규 생성
   - 기존 `sendEmail` 호출부에 `sendKakao` 병렬 호출 추가 (이메일 실패 시에도 알림톡 발송)
   - 사용자 동의 여부(`marketing_agreed`)와 무관하게 거래성 메시지는 발송 가능

### API 공통 패턴

- 인증: 모든 API는 `createClient()` 후 `supabase.auth.getUser()` 필수
- Admin API: `createAdminClient()` 사용 (서비스 롤 키)
- 에러 응답: `NextResponse.json({ error: '메시지' }, { status: 4xx })`
- 이메일 발송 실패는 catch로 무시 (`.catch(() => {})`) — 이메일 실패가 트랜잭션을 막으면 안 됨

### 마이그레이션 파일 네이밍

```

0006_branch_manager.sql
0007_...
```
숫자 순서 유지, `supabase db push` 전 로컬 테스트 필수

