## GAP 1. 카테고리 체계 — 가장 먼저 해결해야 할 구조 문제

### 현재 상태 (문제점)

현재 플랫폼은 카테고리가 **3군데에 제각각 다르게 정의**되어 있습니다.

| 위치 | 현재 카테고리 값 | 문제 |
|------|--------------|------|
| 클래스 (`attributes.craft_type`) | 자유 텍스트 (강사가 직접 입력) | 표준화 불가, 필터 작동 안 됨 |
| 상품 (`product_categories` 테이블) | 레진, 몰드, 색소, 장식재, 도구, 패키지, 기타 | 레진아트 재료 중심, 다른 장르 재료 수용 불가 |
| 작품 (`artworks.category` 텍스트) | 레진아트, 비즈공예, 자수, 석고아트, 캔들, 페인팅, 기타 | 프론트 하드코딩, DB 비정규화 |

**결과:** 강사가 "캔들" 클래스를 등록해도 카테고리로 검색되지 않고, 캔들 재료를 판매하려 해도 상품 카테고리에 적합한 분류가 없음.

### 구현 범위

#### 1) DB: `craft_categories` 테이블 신설

```sql
CREATE TABLE craft_categories (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  code        text UNIQUE NOT NULL,      -- 'resin', 'candle' 등
  name        text NOT NULL,             -- '레진아트'
  name_en     text,                      -- 'Resin Art'
  parent_id   uuid REFERENCES craft_categories(id),  -- NULL = 대카테고리
  sort_order  int DEFAULT 0,
  icon_url    text,
  is_active   boolean DEFAULT true,
  created_at  timestamptz DEFAULT now()
);
```

#### 2) 기존 테이블 연결

```sql
-- classes: craft_type 텍스트 → 카테고리 FK로 교체
ALTER TABLE classes
  ADD COLUMN category_id uuid REFERENCES craft_categories(id),
  ADD COLUMN sub_category_id uuid REFERENCES craft_categories(id);

-- products: 카테고리 FK 추가
ALTER TABLE products
  ADD COLUMN category_id uuid REFERENCES craft_categories(id);

-- artworks: category 텍스트 → FK로 교체  
ALTER TABLE artworks
  ADD COLUMN category_id uuid REFERENCES craft_categories(id);

-- instructor_profiles: 전문 장르 배열 → FK 배열
ALTER TABLE instructor_profiles
  ADD COLUMN specialty_categories uuid[] DEFAULT '{}';
```

#### 3) UI 변경 포인트

- **홈페이지**: 장르 탭 필터 (현재 지역 탭만 있음 → 장르+지역 복합 필터)
- **클래스 목록**: 사이드바 또는 상단 카테고리 필터
- **강사 등록 폼**: 전문 장르 멀티 선택 (현재 자유 텍스트)
- **클래스 등록 폼**: 대/소카테고리 드롭다운 (현재 자유 텍스트)
- **상품 등록**: 카테고리 선택 (8개 장르 + 소카테고리)
- **작품 업로드**: 카테고리 선택 드롭다운 교체

## GAP 2. 상품 입점사(멀티벤더) 시스템 — 파트너십 모델 A 실현의 핵심

### 현재 상태 (문제점)

현재 재료 쇼핑몰은 **관리자가 직접 재고를 등록하는 자사몰** 구조입니다.

- 외부 공급사(파트너)가 자기 상품을 직접 등록할 수 없음
- 판매 수익이 모두 플랫폼으로 귀속 (공급사 정산 불가)
- 상품에 `vendor_id` 또는 `seller_id` 필드 없음
- `branches` 테이블에 `commission_rate` 필드가 있지만 주문 생성 시 전혀 활용 안 됨

**사업 보고서 목표 (파트너십 모델 A):**  
"플랫폼 내 공식 재료몰 입점, 강사가 클래스 준비물 안내 시 파트너 제품 자동 연결, 수강생이 클래스 예약 후 재료 구매까지 원스톱"

---

### 제안: 멀티벤더 구조 설계

#### 수수료 구조 (3가지 모델)

**모델 1 — 플랫폼 직매입 (현재 구조 유지)**
```
입점사 납품가로 매입 → 플랫폼이 소매가 책정 → 마진 100% 플랫폼
적용: 레진 핵심 재료 직접 소싱 시
```

**모델 2 — 위탁 판매 (추천)**
```
입점사가 상품 등록 + 재고 관리
수강생이 구매 → 플랫폼 수수료 공제 후 입점사 정산
수수료율: 판매가의 15~20% (협의)
```

**모델 3 — 링크 연동 (외부몰 연계)**
```
입점사 자사몰 URL 연결 → 클릭 후 외부 구매
플랫폼: CPA(구매 건당) 또는 월정액 노출 수수료
```

**추천 시작점: 모델 2 (위탁 판매)** — 재고 리스크 없이 수수료 수익 확보

#### DB 변경 사항

```sql
-- 1) 벤더(입점사) 테이블 신설
CREATE TABLE vendors (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id         uuid REFERENCES users(id),       -- 입점사 담당자 계정
  business_name   text NOT NULL,                   -- 상호명
  business_no     text,                            -- 사업자등록번호
  representative  text,                            -- 대표자명
  commission_rate numeric(5,2) DEFAULT 15.00,      -- 플랫폼 수수료율 (%)
  payout_account  jsonb,                           -- 정산 계좌
  status          text DEFAULT 'pending'           -- pending/approved/suspended
    CHECK (status IN ('pending','approved','suspended')),
  approved_at     timestamptz,
  created_at      timestamptz DEFAULT now()
);

-- 2) products 테이블에 벤더 연결
ALTER TABLE products
  ADD COLUMN vendor_id    uuid REFERENCES vendors(id),  -- NULL = 플랫폼 직영
  ADD COLUMN vendor_price numeric(12,2),                -- 입점사 공급가
  ADD COLUMN commission_rate numeric(5,2);              -- 개별 수수료율 (vendor 기본값 오버라이드)

-- 3) orders 테이블에 정산 필드 추가
ALTER TABLE orders
  ADD COLUMN platform_fee    numeric(12,2) DEFAULT 0,
  ADD COLUMN vendor_payout   numeric(12,2) DEFAULT 0,
  ADD COLUMN payout_status   text DEFAULT 'pending'
    CHECK (payout_status IN ('pending','paid','hold'));

-- 4) 벤더 정산 테이블 (강사 payouts와 동일 구조)
CREATE TABLE vendor_payouts (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  vendor_id       uuid REFERENCES vendors(id) NOT NULL,
  period_year     int NOT NULL,
  period_month    int NOT NULL,
  total_sales     numeric(12,2) DEFAULT 0,
  total_platform_fee numeric(12,2) DEFAULT 0,
  total_payout    numeric(12,2) DEFAULT 0,
  order_count     int DEFAULT 0,
  status          text DEFAULT 'pending'
    CHECK (status IN ('pending','paid','hold')),
  paid_at         timestamptz,
  UNIQUE(vendor_id, period_year, period_month)
);
```

## GAP 3. 강사 에이전시 시스템 — 상품 벤더와 대칭되는 강사 공급 구조

### 현재 상태 (문제점)

현재 플랫폼은 **개인 강사만 직접 신청·승인**되는 구조입니다.

- 공방, 스튜디오, 강사 에이전시가 소속 강사 여러 명을 묶어서 입점할 방법 없음
- 에이전시가 강사를 공급하더라도 강사 각각이 개별 신청해야 함
- 에이전시 단위 수익 집계 및 정산 구조 없음
- 상품 공급사(벤더)와 거의 동일한 구조임에도 현재는 미구현 상태

**사업 보고서와의 연결:**  
파트너십 모델 E(지부 네트워크 파트너) 및 모델 B(클래스 콘텐츠 파트너)를 체계화하려면 에이전시 단위의 강사 공급 구조가 필수입니다.

---

### 개념: 벤더(상품)와 에이전시(강사)의 대칭 구조

| 항목 | 벤더 (상품 공급사) | 에이전시 (강사 공급사) |
|------|:---:|:---:|
| 플랫폼과 계약 주체 | 법인·사업자 | 법인·사업자 |
| 공급 자원 | 재료·상품 | 강사 인력 |
| 플랫폼 수수료 | 판매가의 15% (협의) | 결제액의 10% (동일) |
| 정산 방향 | 플랫폼 → 벤더 | 플랫폼 → 에이전시 → 강사 |
| 대시보드 | 상품 관리 + 정산 | 소속 강사 관리 + 정산 |
| 관리 화면 | `/admin/vendors` | `/admin/agencies` |

---

### 수익 분배 구조 — 플랫폼 직접 정산 + 에이전시별 수수료율 설정

플랫폼이 강사와 에이전시 양쪽에 직접 정산하되, 에이전시별로 협의된 수수료율을 적용합니다.

```
수강생 결제: 100만 원
    ├── PG 수수료:          3.3만 원  (고정)
    ├── 플랫폼 수수료:     10.0만 원  (고정)
    ├── 에이전시 수수료:   설정값 %   (에이전시별 개별 협의)
    └── 강사 직접 수령:    나머지     ← 플랫폼이 강사 계좌로 직접 지급
         (에이전시도 플랫폼이 에이전시 계좌로 직접 지급)
```

**에이전시 수수료율 예시별 강사 수령액**

| 에이전시 수수료율 | 강사 수령 | 에이전시 수령 | 플랫폼 수수료 | PG |
|:---:|:---:|:---:|:---:|:---:|
| 0% (개인 강사 동일) | **86.7%** | — | 10% | 3.3% |
| 5% | **81.7%** | 5% | 10% | 3.3% |
| 10% | **76.7%** | 10% | 10% | 3.3% |
| 15% | **71.7%** | 15% | 10% | 3.3% |

> **핵심 원칙**
> - 플랫폼 수수료(10%) + PG(3.3%)는 에이전시 계약과 무관하게 고정
> - 에이전시 수수료는 강사 몫(86.7%)에서 분리되어 별도 지급
> - 강사는 자신의 수령율을 에이전시 가입 시 명확히 고지받음
> - 에이전시가 강사에게 직접 지급하지 않으므로 미지급 분쟁 원천 차단

**개인 강사 vs 에이전시 소속 강사 정산 흐름 비교**

```
개인 강사:
  플랫폼 → 강사 (86.7%) 직접 지급

에이전시 소속 강사:
  플랫폼 → 강사 (86.7% - 에이전시율%) 직접 지급
         → 에이전시 (에이전시율%)       직접 지급
```

### 정산 로직 변경 (fees.ts)

```typescript
// lib/utils/fees.ts

const PG_RATE       = 0.033
const PLATFORM_RATE = 0.10

export function calcBookingFees(gross: number, agencyRate: number = 0) {
  const pgFee           = Math.round(gross * PG_RATE)
  const platformFee     = Math.round(gross * PLATFORM_RATE)
  const agencyFee       = Math.round(gross * agencyRate / 100)   // 에이전시별 설정값 적용
  const instructorPayout = gross - pgFee - platformFee - agencyFee

  return { pgFee, platformFee, agencyFee, instructorPayout }
}

// 사용 예시
// 개인 강사: calcBookingFees(1_000_000, 0)
//   → instructorPayout: 867,000 / agencyFee: 0
// 에이전시 10%: calcBookingFees(1_000_000, 10)
//   → instructorPayout: 767,000 / agencyFee: 100,000
// 에이전시 15%: calcBookingFees(1_000_000, 15)
//   → instructorPayout: 717,000 / agencyFee: 150,000
```

월 정산 Cron에서 에이전시별 집계 → `agency_payouts` 생성 → 어드민이 강사 payouts와 함께 일괄 지급.

에이전시별 수수료율은 어드민에서 계약 시 직접 설정하고, 이후에도 수정 가능합니다.

```
/admin/agencies
  ├── 에이전시 목록
  │     ├── 에이전시명
  │     ├── 소속 강사 수

  │     └── 정산 계좌 확인
  └── 에이전시 상세
```

## GAP 7. 작품 마켓 수수료 — 거래량·단가 연동 구간별 구조

### 현재 상태

- `artwork_orders`: 구매자가 결제 → 판매자(수강생)가 100% 수령
- 플랫폼 수수료 필드 없음
- 마켓 거래에서 플랫폼 수익 발생 없음

### 시장 비교

| 플랫폼 | 수수료 | 비고 |
|--------|:------:|------|
| 아이디어스 | 20% | 국내 최대 핸드메이드 마켓, 작가 불만 多 |
| 카카오선물하기 | 10~15% | 입점 심사 까다로움 |
| Etsy (해외) | 6.5% + 리스팅비 | 글로벌 핸드메이드 |
| 당근마켓 | 3% | 결제 수수료만 |
| **오센틱아트 (목표)** | **5~10%** | **아이디어스 대비 절반 이하, 거래량·단가 우대** |

### 확정 수수료 구조

> 아이디어스(20%) 대비 최대 절반 이하 — 핸드메이드 작가 유인 및 수강생 판매 활성화 목표

| 조건 | 수수료율 | 판매자 수령 | 적용 기준 |
|------|:-------:|:----------:|---------|
| 기본 (개인 월 거래 100건 미만) | **10%** | 90% | 판매자 개인 월 거래량 |
| 개인 월 거래 100건 이상 | **8%** | 92% | 판매자 개인 월 거래량 |
| 개인 월 거래 200건 이상 | **5%** | 95% | 판매자 개인 월 거래량 |
| 단가 50만 원 이상 | **5%** | 95% | 건별 즉시 적용 |

> **중복 적용 원칙:** 거래량 조건과 단가 조건이 동시에 해당되면 낮은 수수료율 적용

### 리셋 기준 — 매월 1일 초기화 + 하락 시 1개월 유예

```
기준:  판매자 개인 월 거래량 (매월 1일 카운터 초기화)
올라갈 때 (수수료 하락):  즉시 적용
내려갈 때 (수수료 인상):  1개월 유예 후 적용

예시)
  1월: 230건 → 5% 적용
  2월: 85건  → 유예 적용 (전월 5% 1개월 유지)
  3월: 85건  → 10% 적용 (유예 종료)

  4월: 120건 → 8% 즉시 적용 (인하 = 즉시)
  5월: 250건 → 5% 즉시 적용 (인하 = 즉시)
```

**수수료 계산 예시:**

```
작품 단가 10만 원 / 개인 이번 달 적용 수수료율 10% (기본)
  ├── 판매자 수령: 9만 원 (90%)
  └── 플랫폼 수수료: 1만 원 (10%)

작품 단가 10만 원 / 개인 이번 달 적용 수수료율 8% (전월 100건↑)
  ├── 판매자 수령: 9만 2천 원 (92%)
  └── 플랫폼 수수료: 8천 원 (8%)

작품 단가 60만 원 (단가 우대, 거래량 무관)
  ├── 판매자 수령: 57만 원 (95%)
  └── 플랫폼 수수료: 3만 원 (5%)
```

```typescript
// 거래 건수 → 수수료율 변환
function rateFromCount(count: number): number {
  if (count >= 200) return 5
  if (count >= 100) return 8
  return 10
}

// 주문 생성 시 호출 — seller_artwork_stats의 applied_rate 사용
export async function calcArtworkFee(price: number, sellerId: string) {
  // 단가 50만 원 이상: 거래량 무관 즉시 5%
  if (price >= 500_000) {
    const platformFee = Math.round(price * 5 / 100)
    return { platformFee, sellerPayout: price - platformFee, rate: 5, reason: 'high_value' }
  }

  // 판매자의 이번 달 적용 수수료율 조회
  const now = new Date()
  const stats = await getSellerArtworkStats(sellerId, now.getFullYear(), now.getMonth() + 1)
  const rate = stats?.applied_rate ?? 10  // 이력 없으면 기본 10%

  const platformFee  = Math.round(price * rate / 100)
  const sellerPayout = price - platformFee
  return { platformFee, sellerPayout, rate, reason: 'seller_tier' }
}
```

### 월초 수수료율 갱신 Cron (매월 1일 00:00 실행)

```typescript
// app/api/cron/artwork-rate-refresh/route.ts

async function refreshSellerArtworkRates(year: number, month: number) {
  const [prevYear, prevMonth] = getPrevMonth(year, month)

  // 전월 거래량 집계
  const prevStats = await db
    .from('seller_artwork_stats')
    .select('seller_id, order_count, applied_rate')
    .eq('year', prevYear).eq('month', prevMonth)

  for (const prev of prevStats) {
    const earnedRate = rateFromCount(prev.order_count)  // 전월 실적 기반 산출 요율
    const prevApplied = prev.applied_rate               // 전월 실제 적용 요율

    // 하락(수수료 인상)이면 1개월 유예 → 전월 적용 요율 유지
    // 상승(수수료 인하)이면 즉시 적용
    const appliedRate = earnedRate > prevApplied ? prevApplied : earnedRate
    const isGrace     = earnedRate > prevApplied

    await db.from('seller_artwork_stats').upsert({
      seller_id:   prev.seller_id,
      year,  month,
      order_count: 0,            // 새 달 카운터 초기화
      applied_rate: appliedRate,
      earned_rate:  earnedRate,
      is_grace:     isGrace,
    })
  }
}
// 주문 생성 시 해당 seller_artwork_stats.order_count += 1 (Trigger 또는 API)
```

## GAP 8. 소비자 보호 장치 — 거래 유형별 에스크로·취소·분쟁 체계

### 현재 상태 (문제점)

현재 플랫폼은 결제와 정산 사이의 소비자 보호 장치가 전무합니다.

| 거래 유형 | 리스크 | 현재 보호 장치 |
|---------|--------|-------------|
| 클래스 예약 | 강사 갑작스런 취소, 노쇼 | 없음 |
| 재료 쇼핑몰 | 미배송, 상품 불량, 환불 거부 | 없음 (전자상거래법 미준수) |
| 작품 마켓 | 허위 설명, 미발송, 작품 손상 | 없음 |

> **전자상거래법 리스크:** 재료 쇼핑몰(벤더 시스템)을 오픈하는 즉시 전자상거래법 적용 대상이 됩니다.  
> 청약철회 7일 미보장 시 과태료(500만 원 이하) + 소비자 분쟁 발생.

### 거래 유형별 보호 설계

#### 1) 클래스 예약 — 취소 정책 표준화

```

D-3 이전 취소  →  100% 환불
D-1 ~ D-2 취소 →   50% 환불
당일 취소       →    0% 환불 (노쇼 포함)

강사 귀책 취소 (강사가 취소):
  → 수강생 100% 환불 + 강사 패널티 포인트 누적
  → 패널티 3회 누적 시 관리자 검토 → 계정 정지 가능
```

#### 2) 재료 쇼핑몰 — 전자상거래법 준수 + 구매확정 에스크로

**법적 의무 사항 (전자상거래 등에서의 소비자보호에 관한 법률):**
- 청약철회: 수령일로부터 **7일 이내** 무조건 환불
- 교환·반품 배송비: 소비자 귀책 시 소비자 부담, 판매자 귀책(불량·오배송) 시 판매자 부담
